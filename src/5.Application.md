# LLM透かし　ー　応用編

LLM透かしの基礎を理解している上で、もっと発展的な話をしたく、こと章で筆を進んでいます。やはり、よく基礎を理解している皆さんが、少なからず疑問が浮かべているでしょう。例えば、
- すべての単語を単純に二つのリストに振り分けることは、生成に影響しないか?
- LLM透かしはすべての種類のテキストに適用できますか?
- 透かしを簡単に外れる方法はありますか？

など、色々の問題がもし皆さんの中に湧いてくれたら、この分野を二年ほど追い続けている人間として、それ以上うれしいことがありません。だから、ここで、いくつかの研究の最前線の知見を紹介し、少しでも皆さんの疑問を晴れるになったら幸いだと思います。

## 性能に影響がありますか？

これまで紹介されたLLM透かしは、トークンの染色においては、全体的に一つの振り分け方を徹しています。これの利点として、まずは理解しやすいです。しかし、これを実用化するために、いくつかの問題点が存在しております。例えば、もし透かしがいれたら、赤いトークンが選択できなくなるではないかという疑惑があります。

例えば、以下の透かし入りの結果をよく見ると：
![](../pics/chap5/麦茶と紅茶.svg)
「麦茶」が緑のトークンになり、「紅茶」が赤いトークンになるということが判明できます。もし、その攻撃者が麦茶と紅茶の「色」を知りたい場合、一番簡単なやり方として、モデル十回クイズをします。
具体的には、その単語を十回繰り返していうようにのを命令し、その単語が果たして繰り返せるかどうかを観察すればいいです。
例えば、「『麦茶』を十回言いなさい」と「『紅茶』を十回言いなさい」の間、もし普通の状態だと、ちゃんと十回くらい言えるはずです。もし、どっちが十回に言えないなら、背後に何かあるはずです。それは、あるトークンが赤いトークンである判断材料にもなりうるです。

それでは、実際に試してみましょう。前章のコードを整理し、これから透かしを呼び出し方として、以下のコードを用意しました：
```python
from watermark_utils import Watermark_Config, watermark_model
model_name = "google/gemma-3-1b-it"
green_red_list_ratio = 0.5

meaningful_start_at = 237
meaningful_end_at = 255968

wm_config = Watermark_Config(
    watermark_type="v2",
    gamma=4,
    start_at=meaningful_start_at,
    end_at=meaningful_end_at,
    green_red_ratio=green_red_list_ratio,
)
wm_model = watermark_model(model_name, wm_config, device="cpu")
```
あくまでも、前章のコードを整理清書したもので、特に新しいものはない。
```python
messages = [[{
    "role": "user",
    "content": [{
        "type": "text", 
        "text": "**麦茶**を十回言いなさい："
    },],},],
]

response: list[str] = wm_model.generate(
    messages=messages, do_watermark=True, max_new_tokens=256
)
prompt, output = response[0].split("model", maxsplit=1)
print(prompt)
print(output)
print(
    "偏差値 -> ",
    wm_model.detect_watermark(
        output, visualization="../pics/chap5/十回麦茶.svg", title="「麦茶」を十回言いなさい"
    ),
)
```
そして、結果として:
![](../pics/chap5/十回麦茶.svg)

こりゃ十回だけではないだな。それでは、もし同じ指令を「紅茶」として入れ替わるのは何か起こりますか？
![](..\pics/chap5/十回紅茶.svg)

なるほど、要するに、透かしが入ってとしても、別に赤いトークンが出力できなくなるわけではなく、あくまでも、そのプロンプトに応じて、緑のトークンの頻度を上げるだけだという認識で妥当だと思います。

## 動的ハッシュ

それでは、静的振り分け（全体的に一つの振り分けパターンしかない）は本当になんの問題がないかというとそうではありません。もしそこに攻撃者が存在していって、その人我々の透かしを乗っ取るとたくらんでいるとしましょう。その攻撃者が大量の計算資源が持ち、そして、今我々が使っている透かし技術も理解しています。これは、ケルクホフスの原理と言います。いわゆる、暗証キー以外の仕組みは全部公開しているなお安全なシステムこそが、本当に安全のシステムであると。
![alt text](../pics/chap5/Kerckhoffs.png)

そして、透かしにおいての暗証キーは、いわばトークンリストの振り分け方に当たる。そこで、もし読者の皆さんが攻撃者だとすれば、どう攻撃を仕掛けますか？

そう、極めて単純な手法で、大量のモデルの出力を搔き集め、総当たりで単語の頻度を計算します。その頻度が、標準の自然言語データセットと必ずどこかずれが発生します。そこが、緑のトークンと赤いトークンを見分ける判断材料になります。

それでは、こういう攻撃はどう防げるのかというと、それも極めて単純である。振り分けのパターンの通り数を増えばいいです。一番簡単の手法して、前のトークンを次のトークンの暗証キーの一部として使います。

![](../pics/chap5/動的ハッシュ.svg)

上の図のように、静的ハッシュというのは、予め決められた振り分け方が生成の全過程のおいて一貫されるような手法です。そして、動的のハッシュというのは、生成するごとに、前のトークンを取り入れて再染色を行います。

こういうやり方の利点として、総当たりのパターン探しの空間のサイズがトークンの数の倍になることです。例えば、静的ハッシュの場合、とりあえず生成された文書の中の単語頻度と自然の文書の中のそれと比較すればいい話に対して、動的ハッシュの場合、例えば、前のトークンが「東京」を意味する場合、自然言語のデータセットの中の、すべて「東京」の後の単語の頻度とモデル生成した「東京」の後の単語の頻度を比較する必要があります。いわゆる、条件付き頻度で比較する必要があります。

それでは、これがいかにコードとして実装するのかこれから説明したい部分です。これは別に難しい話ではなく、今もっているコードを少しだけ調整したらできる話です。

しかし、こういった動的ハッシュは別に欠点がないわけではないです。例えば、以下のような攻撃が動的ハッシュには特段有効となります：

![emoji.png](../pics/chap5/emoji.png)

例えば、「単語の間ごとに絵文字を入れなさい」と指示したら、動的ハッシュが完全に破壊することが可能となります。前のトークンが全部絵文字になってしまい、そのあと、全部の絵文字を消せば、前のトークンが全部変わります。もちろん、これはいくつかの修正により改善できるが、でもそれは読者の挑戦として残します。

## 透かしの放射性
![](../pics/科学子/放射性.png)
放射性といっても、別に原子物理学の中のあの放射性ではなく、透かしがいろんな操作を経た後にまだ残る性質を指しています。一番簡単な例をすると、透かし入りの文章がChatGPTに言い直しの依頼を出し、その解答の中にまだ透かしが検出できることがあります。例えば、透かし入りモデルに、以下の例を生成する

![](../pics/chap5/sf_wm.svg)

そして、ChatGPTに自分の言葉で再説明するという指示を出し[1]：
![alt text](../pics/chap5/chatgpt.png)

その解答の中の透かしを測るとすると、こうなります：
![](../pics/chap5/paraphrased.svg)

シグナルはある程度弱くなってしまうものの、しっかり残っています。この性質は単純な書き換え指令の他例えば、透かし入りのデータセットをモデルで学習すれば、そのモデルの出力の中に、少なからずLLM透かしを検出することができます。同じく、透かし入りのデータでファインチューニングするモデルも、透かしのパターンを「無自覚」に学習したこともあります。その中に、特に面白いのは、もしRAGのデータセットの中に、透かし入りのデータが存在しているとしたら、この放射性を活用し、それの検出することができます。

本書冒頭部分の例を思い出してほしいです。新聞社がAI会社を提訴した理由として、自分の記事が無断に使ったという疑いがあります。しかし、それの証明が難しく、AI会社にデータベースの中身を開示してくれるというのは困難です。もし、記事の中に、どこかでこういう透かしが入っているとしたら、もちろん記事を使っているサービルの出力の中にも、透かしが検出することができます。こういった技術を活用すると、そういう濫用の問題をある程度解決できるじゃないかなと思っております。
